# 八步流水线详解（Task Pipeline Reference）

> 配合 `SKILL.md` 使用。**定位**：本文件描述的是核心工作流「阶段 2（小批量执行）」内部单个批次的执行细节；项目级节奏（先讨论方案 → 小批量执行 → 分层验收）以 `SKILL.md`「核心工作流」一节为准。每步给出：目标、动作、验收线、常用命令思路。

## 步骤 0：开工核对

**目标**：在动手前把"环境、资源、他人改动、已有记录"四件事看一遍，避免 80% 的事故。

**检查清单**：

- [ ] `git status`：工作区干净；未提交改动是预期的吗？
- [ ] `git log --oneline -5` 与 `@{u}`：本地是否落后远端？落后要 ff/merge 后再改
- [ ] 共享文件（可能被协作者修改的文档、工作流、配置文件、AGENTS 类约定）：`git fetch` 后对比，防止覆盖他人改动
- [ ] 待办清单：本次要做的事是否已有人做过 / 有记录可查？避免重复提问、重复实验
- [ ] 资源占用：提交批量任务前查 GPU 显存（`nvidia-smi`）、端口（`ss -tln`）、任务队列、磁盘水位
- [ ] 范围：本次任务边界是什么？哪些相邻问题"看到了但不顺手做"（记入待办即可）

**验收线**：能一句话说清楚——"在哪个环境、基于哪个版本、这次只做 X，资源条件 OK，Y/Z 留给下次"。

## 步骤 1：澄清问题

**目标**：把含糊的问题报告变成可执行的三元组。

- **环境**：哪台机器 / 哪个环境栈（生产 vs 测试）/ 哪个分支 / 哪个进程
- **时间点**：几点几分（含时区）；日志与数据库的时间窗按这个来截
- **错误原文**：逐字错误信息、HTTP 码、日志行；截图对模型不可读时请用户粘贴文本

**不做**：问题含糊时直接开跑。宁可多问一句，不要埋头跑偏（大量时间是花在"猜错环境/猜错时间窗"上的）。

**注意**：先确认环境是否只有你在用（是否有并发工作流/他人会话会污染判断）。

## 步骤 2：取证（证据链）

**目标**：现象 → 根因的每一步都有 ≥2 个独立来源印证。

**取证顺序（从外到内）**：

1. 入口层：网关/负载均衡/客户端访问日志（谁、何时、什么请求、什么响应码）
2. 业务层：服务日志（该请求在系统内的处理路径、阶段、错误）
3. 数据层：数据库记录（状态、时间戳、关联记录）——**表里没有行、行停在中途状态，都是证据**
4. 对端探测：直接请求上游/对端服务（注意用"无副作用"的姿势：只读、不带 key、或带 key 但不落盘）
5. 代码路径确认：读源码确认"这一层在什么条件下做出这个判断"（UI 状态不是证据源）

**技巧**：

- 双向坐实：正向复现 + 反向验证（"如果根因是 X，那么 Y 应该也成立/不成立"），两条腿走路
- 无痕也是线索：某个环节完全没有记录 = 请求从未到达那里 = 拒绝发生在更早层
- 假象层识别：HTTP 200 可能包着业务错误信封；某客户端把错误吞掉只留通用状态——要用差异说话（修前/修后、成功/失败样本各留快照）
- 取证本身记账：探测会写审计日志、真实调用会在对端建任务/计费——先声明，跑完记录

**验收线**：能画出"现象 ← 层 A（证据）← 层 B（证据）← 根因"的链条，每段都有记录/命令可复现。

## 步骤 3：最小修改

**目标**：只修一个根因，走正规路径，带测试。

- 拆出唯一根因；"顺便"的事记入待办，不做
- 改配置走管理 API/官方工具，不用裸 SQL、不直接改线上文件（绕过校验 = 后续所有调查失真 + 缓存/审计不同步）
- 改共享/他人文件：先同步到最新，再做最小增量；保留他人内容
- 每处改动配测试，先复现失败（红）再验证修复（绿）
- 修改范围说明书：这处改动会影响的调用方/下游列出来，供步骤 4 决定验证深度

## 步骤 4：验证

**目标**：修复在"真实路径"上成立，且影响面没有波及其他。

- 分层：单元（函数级）→ 集成（进程内全链路）→ 端到端（真实二进制/真实端口/真实依赖或真实上游桩）
- 端到端必须跑通一次**真实用户路径**（提交 → 落库 → 回调/轮询 → 产物），模拟器/桩只做补充
- 否定断言也要证据：声称"不受影响"的相邻功能，用运行时长/日志/字节比较佐证
- CI 红先归因：本次引入还是既有问题；既有问题单独立项，不混入本次提交
- 配置类修改验证两侧：写侧（提交后读回）与读侧（运行时实际取到的值）

## 步骤 5：收尾

- 提交信息含证据链（现象一句话、根因、修法、验证方式），可链接任务记录/issue
- 清理：临时文件、探针脚本、调试打印、测试数据、残留监听端口
- 复核影响面：其他环境？其他分支？其他调用方？（改共享脚本时尤其要看同步链路是否会覆盖/回退）
- 未提交/遗留的改动清单如实报告，不藏

## 步骤 6：沉淀

- 踩坑与决策写 memory：当日记录（what/why/how）+ 长期条目（事实、决策、教训）
- 批量出现的方法论 → 模板/skill；一次性的查法 → 文档的"排障"章节
- 文档分层：过程叙事（怎么做成的、为什么）进任务记录；稳定契约（接口、架构、口径）进正式文档并随代码走

## 步骤 7：汇报

- 结论先行（一句话），支持证据（数字 + 来源），副作用（包括排查本身的记录/费用/残留）
- 说人话：先大白话，再必要术语；宁可啰嗦不炫技
- 遗留事项与建议下一步，等用户拍板

## 各场景的取证命令思路（只列思路，按环境替换）

| 场景 | 常用动作 |
|---|---|
| 服务状态 | 健康端点 curl、容器状态与重启时间、进程列表与启动参数 |
| 请求链路 | 入口日志按时间窗/用户筛选 → 业务日志同 request_id 串联 → 数据库状态行 |
| 数据层 | 只读 SELECT、状态机分布统计、与"应该有的值"比对（如计数器最大值是否增长） |
| 上游排查 | 无凭据探测路由是否存在（401 vs 404 已能区分"有门 vs 没门"）、带凭据只在目标机上跑、不打印不落盘 |
| 部署验证 | 镜像 ID/容器 ID 与预期比对、版本指纹（bundle 哈希）、外部 URL 验收 |
| 资源 | nvidia-smi、ss -tln、docker ps 与 label（com.docker.compose.project）、df -h |
